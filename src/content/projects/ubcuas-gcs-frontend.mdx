## How I got here

I joined UBC UAS in 2021 as a mechanical team member, which mostly meant I spent the first year trying to figure out what everything did. The team was working on a payload system with a claw mechanism to retrieve objects mid-flight. I was somewhere between contributing and asking questions every five minutes and hoping nobody noticed.

That period turned out to be useful. I built a mental model of the whole system: how the ground control station talked to the drone, how competition rules shaped hardware constraints, how a software command eventually became a physical motion. I just wasn't writing much code yet.

## What I actually built

Once I moved to software, things moved faster because I understood the context.

### Ground control station frontend

Built a lightweight GCS frontend in TypeScript and Svelte. The main view displays mission parameters and a live map showing the drone's current position. The goal was functional over fancy: the right information, visible at the right time, during an active competition flight.

### QR scanner for mission parameters

Competition software generates mission parameters as encoded barcodes. The manual flow was slow and error-prone. I added a QR scanner to the frontend that read the competition-spec codes and sent the decoded parameters as a JSON object directly to the backend endpoint. It removed a manual transcription step that had been a real problem under time pressure.

### Real-time camera streaming

Wrote Python scripts using sockets to extract frames from a machine vision camera and stream them over a custom antenna system. Used both TCP and UDP depending on the tradeoff between reliability and latency for each use case. The end goal was mid-flight object detection: getting usable images to the GCS fast enough for the software to make decisions during the flight.

## What 3rd nationally means in practice

The team placed 3rd nationally. That sounds clean from the outside. From the inside it was a lot of iterations, hardware failures, and last-minute field fixes. Competition conditions are different from development conditions. Things break in different ways when you're on a flight field with a clock running.

The output that actually matters from this experience is learning how to build software that has to work when the hardware is doing something unexpected.
