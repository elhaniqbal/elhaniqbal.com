## Where this came from

A lot of my infra change during my Samsung co-op followed the same tiny liturgy: grab a JIRA ticket, open the Terraform repo, hunt down the file where that kind of resource *usually* lives, copy the block above it, change five values, match the naming scheme from memory, open a PR, wait for Atlantis to plan, notice I fat-fingered one label, push again, wait again.

None of it was too hard. All of it was rote. It was the software-engineering equivalent of hand-copying a recipe because the cookbook is chained to the desk — and I kept thinking a small, very stubborn robot could do the copying while I kept the only part that needs a brain: the review.

tfbot (working name; it changes with my mood) is that robot.

## What it does

You give it a sentence or a JIRA ticket (lol). It gives you back a pull request.

> "need an S3 bucket for the monthly compliance reports, this is for prod"

That turns into a branch with a convention-perfect Terraform block, four gates green, a `terraform plan` running async in CI, and the reasoning stapled to the PR description. You review it and merge — or tell it it's wrong, which is a first-class outcome, not an error.

## The one rule everything else hangs off

**The LLM proposes; deterministic code performs.**

The model is never allowed to write HCL. Letting a language model freehand your infrastructure files is how you get a bucket that's 90% right and 100% unreviewable. Instead, the only thing that crosses the AI boundary is a small, schema-validated *intermediate representation* — a structured "here is what I think you asked for":

```yaml
action: add
resource_type: s3_bucket
params:
  env: prod
  purpose: compliance
confidence: high
```

A Go engine takes that IR and makes the edit surgically, on the syntax tree, with hclwrite. It never regenerates a file from a template. Your existing comments, your slightly cursed block ordering, that one hand-aligned column you're irrationally proud of — all of it survives byte-for-byte. (There is a test literally named `TestApplyAddPreservesExistingBytes`, because I trust myself about as far as I can throw a Terraform state file.)

## Conventions are data, not code

Every Terraform repo has a house style: whether buckets are raw resources or a module, which file they live in, how things get named, which defaults everyone copies without thinking. tfbot learns all of that *before* any AI shows up. A zero-LLM, offline scanner reads the repo and drafts a `recipe.yaml` — the conventions written down as data, ratified once by a human:

<Figure src={scan} alt="tfbot scan output: an inferred conventions table and a drafted recipe.yaml for a Google Cloud Storage module repo">
  `tfbot scan .` on a GCS repo — one command, about a second, no network. It infers the module source, target file, naming scheme, and shared defaults, then hands you a draft `recipe.yaml` to sign off on. Placeholders like `{part1}` stay deliberately dumb; naming things is the one job it refuses to guess at.
</Figure>

That recipe drives a single generic executor. Adding support for a new resource type is a new recipe entry, not a new `if` branch — so the interesting engineering lives in the inference, not in an ever-growing switch statement I would eventually learn to hate.

## Two AI steps, and a wall of boring checks between them

The whole pipeline gives a model a say in exactly two places: extraction at the start (sentence → IR) and one faithfulness judge at the very end (does this diff actually match what was asked?). Everything in between is deterministic gates that cannot be sweet-talked:

- **fmt** — is every edited file canonically formatted?
- **ast-diff** — did *only* the addresses we planned to touch change? (This one hard-fails the run if the model colored outside the lines.)
- **naming** — does the new block match the repo's scheme?
- **terraform validate** — does it actually validate?

And when a gate can't run — no terraform binary, uninitialized workspace — it returns **Skip with a reason**, never a fake pass. Gates degrade honestly or not at all, so the synchronous path works fully offline. The judge can veto; it can never edit. No agents grading agents, no vibes, no "looks good to me 🤖".

My favorite part is what it does when you're vague. Ask for *"another bucket like the analytics one"* and it doesn't guess — it asks you a few questions and touches nothing. Refusing to make something up was a feature I had to build on purpose, and it's the one I'd defend hardest.

## The fine-tune, and the bug it found

The question I left open above — whether a small, self-hosted model can handle extraction about as well as a frontier one — stopped being hypothetical. I fine-tuned Qwen2.5-1.5B-Instruct with QLoRA on a free Colab T4 (a few hundred fabricated repos' worth of gold-labeled requests, never the real fixtures — the point is teaching the *task*, not memorizing any one repo's resource names), quantized it to a ~1GB GGUF, and pointed the exact same pipeline at it via a local `llama-server` instead of the Claude API. Then I ran the real benchmark instead of a vibe check:

| | frontier (Claude) | self-hosted (1.5B, fine-tuned) |
| --- | --- | --- |
| exact-match on held-out requests | 71.2% | 36.1% |
| action / resource-type detection | 95.0% / 97.7% | 95.0% / 95.9% |
| knows when to *ask* instead of guess | 0.79 | 0.33 |
| never silently ships a wrong PR (adversarial corpus) | 22/30 | **28/30** |

The gap is real, but it's not the gap you'd guess. Detecting *what* someone's asking for barely moved — 95%+ either way. Where the small model actually fell down was judging *when to ask a clarifying question instead of confidently guessing*. And the adversarial number is the twist: despite scoring worse overall, the small model shipped fewer silently-wrong diffs than Claude did, because it defaults to asking rather than assuming. Worse extractor, more honest failure mode — a distinction that never would have shown up if I'd only measured raw accuracy.

That clarify-F1 gap turned out to have a precise, fixable cause, not a "small models are just worse" shrug. My synthetic training-data generator enumerates gold examples across a library of fabricated repos, and one code path scaled with corpus size while the "here's an ambiguous request, you should ask a question" and "this is a delete, refuse it" examples were generated at a **flat count of 3 per resource**, regardless of how big everything else got. In the actual corpus that came out to 1,132 confident-answer examples against 66 must-ask-a-question ones — a 17:1 imbalance, and it gets *worse*, not better, as the fabricated repo library grows. A 1.5B model, entirely shaped by this one dataset, dutifully learned the majority lesson: always answer. Two lines of code — scaling those counts with the same knob that scales everything else — took that ratio to under 4:1. Retraining against the fix to confirm the number actually moves is still open; the bug and the fix are both real and already committed.

## A free way to get there, once I stopped being careless

Regenerating that training data means writing a few thousand natural-language tickets from the gold labels, and the tool that does it defaults to a frontier model for phrasing quality. I ran it without checking that default first, for a batch of ticket-rephrasing that didn't need frontier-model reasoning at all, and it burned real money before I caught it and killed it — a genuinely dumb, avoidable mistake, and an instructive one: check what you're about to spend *before* you hit run, not after.

Which is what pushed me to build the option I probably should have had from the start: `--runtime local`, writing every ticket through my own already-running `llama-server` instead of an API call. Free, forever, no key required — which is closer to the actual spirit of "self-hosted" than "self-hosted extraction, but the training data behind it still needs someone else's GPU and credit card."

It did not work on the first try. Left to its own devices, the 1.5B model's instinct — given a spec like "convey these facts: team=infra, purpose=backups" — was to just echo that shape back: `resource bigquery_dataset bigquery_dataset { team = "infra", purpose = "backups" }`. Training on tickets that already look like the answer would have defeated the entire point of the corpus. Telling it not to do that, explicitly, in the system prompt, helped a little and not enough — still an 80% rejection rate on a small test batch. What actually fixed it was two concrete worked examples showing the exact transformation (spec-with-facts *in*, natural sentence *out*) rather than abstract rules about what not to do. That dropped the reject rate to about 5% on a larger run, with a heuristic filter and a corrective retry loop catching everything that still slipped through — skipped and counted, never smuggled into the corpus, the same "Skip with a reason, never lie" instinct the gate pipeline already had.

It's not equivalent to the frontier-model path — noticeably more templated phrasing, real item loss, one call per example instead of Claude's batches of eight — and I've documented that honestly rather than papering over it. But it's a real, working, zero-cost way to close the loop, and it exists specifically because I made a $15 mistake and didn't want to make it twice.

## What it is, and where it's going

Right now it hangs together as a vertical slice — a CLI, a local web UI, and a GitHub webhook where a `/tfbot <request>` comment on an issue comes back as a pull request. It's honestly still a workbench more than a product: I'm poking at it in the open, mostly to find out which of my assumptions actually survive contact with a real repo. Human review and Atlantis apply stay exactly where they already are — the aim was never to take people out of the loop, only the tedium.

What's actually left is narrower than it used to be: retrain against the rebalanced data and confirm the clarify-F1 gap closes the way the fix predicts, grow the eval corpus, and eventually earn a real name instead of a placeholder that changes with my mood. The self-hosted question isn't hypothetical anymore — I have the numbers, the honest limitations, and a bug-and-fix story I'd rather publish than hide.

The nice part is the deterministic half never had to care which model wins that experiment: the gates, the AST surgery, the recipe all stay exactly the same. The model is the one swappable piece, which is precisely where I want the uncertainty to live. For now it already does the boring 90% and leaves me the 10% worth doing — and back when that boring 90% *was* the whole Tuesday, that's a trade I'll take.
